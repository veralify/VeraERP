# Veralify — Reality-Check Audit

**Date:** 2026-09-18
**Scope:** Coaching marketplace (Priority 1 revenue stream)
**Method:** Read of repo at `~/veralify` — 38 migrations, 14 Supabase Edge Functions, 9 Next.js route handlers, 14 dashboard pages, git history, `.env`, docs.
**Verification:** `tsc --noEmit` runs clean.

---

## Headline

The code is better than the docs claim, and the business is further from revenue than the code suggests.

The booking → Stripe Connect → webhook → payout-ledger path is genuinely implemented, with atomic slot reservation, rollback on failure, and idempotent webhook handling. That is real engineering, not scaffolding.

But **zero external services are configured**, and **both sides of the marketplace are locked behind paid entitlements** — which makes it structurally impossible to acquire the first coach or the first client. That second point is the single most important finding in this document.

## Blockers to first revenue

Ordered by severity. The first two are the ones that matter.

### 1. Both sides of the marketplace are paywalled — CRITICAL

This is a chicken-and-egg deadlock baked into the product logic.

**Coach side** — `api/stripe/connect/onboarding/route.ts` rejects any user without the `VERALIFY_COACH` entitlement:

```
if (!hasEntitlement(entitlements, 'VERALIFY_COACH')) → 403
```

A coach must therefore buy a subscription before they can even connect a payout account. No coach pays to join a marketplace with no clients.

**Client side** — `src/app/coaches/page.tsx` hides the entire coach listing unless the visitor holds `coach_discovery` or `VERALIFY_PRO`:

```
const canDiscover = hasEntitlement(..., 'coach_discovery') || hasEntitlement(..., 'VERALIFY_PRO');
```

A visitor must therefore buy Pro before they can see that any coaches exist. No client pays to browse an empty directory.

The result: the marketplace cannot bootstrap. Both gates have to come off for launch. They were correct decisions for the *frozen entitlement spec*, and wrong for *acquiring the first hundred users*.

### 2. No external service is configured — CRITICAL

`.env` contains Supabase and Resend only. Missing every key the marketplace needs:

- `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` — no payment can be taken, in test or live mode
- `AGORA_APP_ID`, `AGORA_APP_CERTIFICATE` — no video session can start
- `OPENROUTER_API_KEY` — the entire AI layer is unexercised
- `SENTRY_DSN`, `NEXT_PUBLIC_POSTHOG_KEY` — no error or usage visibility

Every payment path in the codebase has been written but **never executed once against a real Stripe account**. Expect the usual first-run friction: webhook signature mismatches, Connect capability requirements, currency and minimum-amount rules.

### 3. Sessions cannot actually be delivered — HIGH

A client can pay for a coaching session and then has no way to attend it.

- `src/app/dashboard/live/page.tsx` is a 16-line "no live rooms" placeholder
- `supabase/functions/agora-token` exists (149 lines, real token construction) but **nothing in the web app calls it** — the only match for "agora" in `src/` is the generated `database.types.ts`
- `coach_sessions.agora_channel` is populated by nothing

You are one step away from taking money for a service you cannot deliver. This must be closed before the first live payment, not after.

### 4. No booking lifecycle communication — HIGH

`src/emails/` contains waitlist welcome, referral notification, and a rich template. There is **no booking confirmation, no reminder, no cancellation notice** for either party. After paying, a client receives nothing but a Stripe receipt. No-show rates on marketplaces without reminders are severe.

### 5. No cancellation or refund path — MEDIUM

`session_bookings` has a `cancelled` status and a `cancelled_at` column, and the schema enforces the constraint correctly — but no code writes it. There is no refund call anywhere in `src/`. Consequences: every dispute becomes manual Stripe dashboard work, and Stripe Connect chargebacks land on the platform account.

### 6. Coach payout visibility — MEDIUM

The webhook records the platform fee, but coaches have no screen showing what they earned, what is pending, or when it arrives. This is the first question every coach asks in week one.

### 7. Legal entity status — VERIFY BEFORE LIVE MODE

`docs/legal/` contains a certificate of incorporation **and** `tell-hmrc-your-organisation-has-stopped-trading-or-has-never-traded.pdf`.

Stripe Connect platform accounts require an active, verifiable legal entity, and Connect platforms carry regulatory obligations around handling other people's money. If the company has been filed as dormant or non-trading, live-mode onboarding will fail verification — possibly after you have recruited coaches.

Confirm the entity's current status at Companies House and with HMRC before starting live Connect onboarding. I am not a lawyer or an accountant; this needs a professional's read, not mine.

### 8. Scope sprawl — MEDIUM

Against one stated goal (coaching marketplace revenue in 2–3 months), the repo carries:

- a 19-phase, v2.6 master specification covering food AI, communities, live rooms, messaging, moderation, notifications
- an iOS app (`veralify-App/iOS`) plus a macOS target
- an unrelated Arabic-language personal finance app (`money-manager-web-mvp-v1`) with its own SQLite DB, committed into the same repo
- 8 local git branches plus worktree branches
- `docs/SPRINT_TASKS.md`, still written for the abandoned eSIM business

Every one of these competes for the same attention. The plan that follows parks all of them.

## Documentation accuracy

`docs/PROJECT_STATUS.md` claims ~40% complete with eight parallel agents "running". Read literally, that overstates readiness: completion there measures *code written against the frozen spec*, not *capability delivered to a user*. By the measure that matters — can a coach get paid for a session — the honest figure is closer to **70% of the code and 0% of the operation**.

`docs/SPRINT_TASKS.md` is stale by two pivots and should be archived.

---

## The one-sentence summary

Stop writing features; wire up Stripe in test mode, remove the two entitlement gates, give sessions a join link, and run one real booking end to end — everything else in the spec is downstream of that.
