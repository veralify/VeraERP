# Money Manager — iOS

Native SwiftUI app for Money Manager, the Arabic-first (RTL) personal finance
and debt-payoff product. Ported from `../money-manager-web-mvp-v1`.

- **iOS 18+**, Swift 6, strict concurrency
- **Local-first SwiftData** — no server required, works offline
- The `.xcodeproj` is **generated**; edit `project.yml` and re-run `xcodegen`

## Layout

| Path | What it is |
|---|---|
| `MoneyManagerCore/` | Swift package: domain types + the payoff engine. No UI, no persistence. |
| `MoneyManager/` | The app: SwiftData records, design tokens, screens. |
| `MoneyManagerTests/` | App-level tests. |
| `Tools/generate-parity-fixtures.mjs` | Regenerates payoff fixtures from the web engine. |

Keeping the engine in its own package is deliberate: it makes the money maths
testable in seconds without booting a simulator, and stops UI or storage
concerns leaking into it.

## Build and run

```sh
brew install xcodegen          # once
xcodegen generate
open MoneyManager.xcodeproj
```

## Tests

The engine's tests are the fast ones and cover the highest-risk code:

```sh
cd MoneyManagerCore && swift test
```

The whole suite, on a simulator:

```sh
xcodebuild test -project MoneyManager.xcodeproj -scheme MoneyManager \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro'
```

## Parity with the web app

The debt-payoff schedule is the product. `PayoffParityTests` pins this engine
against the web implementation using fixtures generated by the **real**
`server.js` algorithm, so the two surfaces cannot quietly diverge.

The web engine computes in JavaScript doubles; this one uses `Decimal`, because
binary floating point accumulates error across a 16-month amortisation. The
tests therefore assert agreement **to the cent** rather than exact equality.

After any change to the web payoff logic:

```sh
node Tools/generate-parity-fixtures.mjs
cd MoneyManagerCore && swift test
```

A failure means the two products would quote a user different payoff plans.
Treat it as a release blocker, not a flaky test.

## Currency

Money is `Decimal` everywhere — never `Double`. Amounts are formatted as EUR
with en-US grouping to match the web app, so the same figure reads identically
on both surfaces.
